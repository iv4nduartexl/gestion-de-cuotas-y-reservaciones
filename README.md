# Agenda

Multi-tenant SaaS for small businesses in Paraguay: online appointments
(barbershops, clinics, salons) and membership dues (gyms, academies).

Stack: Next.js 16 (App Router, Cache Components) · PostgreSQL (Docker) ·
Drizzle ORM · Better Auth (+ organization plugin) · shadcn/ui (Base UI) · Zod.

## Requirements

- Node.js **≥ 22.12** (see `.nvmrc`; the Better Auth CLI needs it)
- Docker (Docker Desktop or compatible)

## Setup from scratch

```bash
nvm use                      # Node 24
npm install
cp .env.example .env         # then set BETTER_AUTH_SECRET:
openssl rand -base64 32      # paste the output into .env
npm run db:up                # start PostgreSQL (port 54329 by default)
npm run db:migrate           # apply migrations
npm run dev                  # http://localhost:3000
```

If port 3000 is taken, run `npm run dev -- -p 3001` **and** set
`BETTER_AUTH_URL=http://localhost:3001` in `.env` (auth links and origin checks
use it).

In development, emails (verification, password reset) are **printed to the
terminal** running `npm run dev`. Open the link from there.

> **npm version:** use npm ≥ 11.19 (`npm i -g npm@11.19.0`). Older npm on macOS
> drops Linux-only optional packages from `package-lock.json`, and then
> `npm ci` fails in Docker and CI.

## Scripts

| Script | What it does |
| --- | --- |
| `db:up` / `db:down` / `db:logs` | Start / stop / tail the Postgres container (data lives in the `postgres_data` volume) |
| `db:generate` | Generate a SQL migration from `db/schema/*` |
| `db:migrate` | Apply pending migrations |
| `db:studio` | Open Drizzle Studio |
| `auth:generate` | Regenerate `db/schema/auth.ts` with the Better Auth CLI (then patches timestamps to `timestamptz`). Run `db:generate` afterwards |
| `typecheck` / `lint` | TypeScript / ESLint |
| `test` | All Vitest tests (unit + integration) |
| `test:unit` / `test:integration` | Vitest projects. Integration tests run against `cuotas_reservas_test` |
| `test:e2e` | Playwright (builds the app and serves it on port 3100 against the test database) |
| `db:test:setup` | Create/migrate the test database (tests do this automatically) |
| `db:migrate:prod` | Apply migrations with the programmatic runner (what production uses) |
| `cron:run` | Run the scheduled jobs once against the running app (cuotas + reminders, see `docs/cron.md`) |

To wipe the local database: `docker compose down -v`.

## Tests

Postgres must be running (`npm run db:up`). The test database
`cuotas_reservas_test` (configured in the committed `.env.test`) is created,
migrated and **emptied** at the start of every integration and e2e run.

```bash
npm test                     # unit + integration (Vitest)
npx playwright install chromium   # once
npm run test:e2e             # end-to-end (Playwright)
```

- `tests/unit/`: phone, money, time-zone, slug and validation helpers.
- `tests/integration/`: the data layer against a real database. Two tenants
  per test; asserts that one can never read or change the other's data, and
  that composite foreign keys and the availability exclusion constraint hold.
- `tests/e2e/`: browser flows: onboarding, clients, services, weekly schedule,
  blocked slots, switching businesses, sign-out and cross-tenant 404s.

## Multi-tenancy rules

- Every domain table has an `organizationId` and every query is scoped to it.
- Get the organization **only** from `getTenantContext()` (server-side
  session + membership check). Never accept an `organizationId` from the client.
- In Server Components use `getTenantContextOrRedirect()`, inside a
  `<Suspense>` boundary (Cache Components requirement for session reads).
- Server actions start with `authorizeAction(permission, { product })` and call
  functions in `lib/data/`. Those take the tenant context and filter every
  query by its organization.
- Child tables use composite foreign keys `(organization_id, x_id)`, so the
  database rejects rows that mix two tenants.
- Organizations are created only via the onboarding server action (which also
  writes `business_settings`); the public `/organization/create` and
  `/organization/update` endpoints are disabled.

## Design system

- Tokens live in `app/globals.css`: blue primary (#1D4ED8), navy sidebar
  (#0B2A5B), coral accent for highlights, green/amber only for status.
  Font: Plus Jakarta Sans. Brand name and tagline: `lib/brand.ts`.
- Every page starts with a `PageHeader` whose description says what the page
  is for; empty sections use `EmptyState` with an explanation and next step.
- Success feedback is a toast (`sonner`): return `{ message }` from an action
  (shown by `useFormAction`) or redirect with `withFlash(path, key)`.
- Wording adapts to the business type via `vocabularyFor()`; solo businesses
  never see "Equipo" and services are auto-assigned to their one person.

## Appointments and online booking

- Each business has a public page at `/{slug}`: service → person (team mode)
  → day and time → name + phone. No account needed.
- Double booking is impossible: an exclusion constraint on `appointments`
  rejects overlapping active turnos (pending/confirmed) of the same person,
  even when two clients submit at the same moment.
- Available times come from `lib/availability.ts` (weekly hours minus días
  libres, existing turnos and the break between turnos), and are re-checked on
  the server before inserting.
- Rules per business (Configuración → Reservas online): auto-confirm or
  manual, minimum notice, how far ahead, time step, break, and how late
  clients can cancel from their private link.
- Anti-abuse (no external service): hidden honeypot field, per-IP and
  per-phone rate limits stored in Postgres (`booking_attempts`), and at most 3
  upcoming turnos per phone. `RATE_LIMITS=off` disables limits (e2e only).

## Memberships (cuotas)

- `plans` (price + interval: weekly or every 1–12 months) → `enrollments`
  (client + plan, active / paused / cancelled, personal price snapshot) →
  `charges` (one cuota per period) → `payments` (several per cuota: partial
  payments are allowed).
- Cuotas fall due on the enrollment's start day of each period (Jan 31 →
  Feb 28 → Mar 31). Date math is on calendar dates, never instants.
- Cuotas are generated automatically and idempotently (`syncCharges`, unique
  per enrollment + period) up to 7 days ahead: whenever the cuotas pages load,
  and via the scheduled job `POST /api/cron/run` (see `docs/cron.md`).
- Stored status is `pending | paid | void`; "Parcial" and "Vencida" are
  derived (grace days are configurable), so nothing goes stale.
- Payments lock the cuota row: concurrent payments can't exceed the debt.
  Pausing stops billing (paused periods are never billed); cancelling voids
  future unpaid cuotas.

## Explaining the app (UX conventions)

New owners must understand what each section is for and what to do next:

- **One source of truth for help copy:** `lib/help-content.ts`
  (`sectionHelp(section, settings)`, `GLOSSARY`, example services and plans
  per business type). The sidebar subtitles, "¿Para qué sirve?" panels, the
  welcome tour and the setup guide all read from it. Change the wording
  there, not in pages.
- **Navigation** (`lib/navigation.ts`) has two groups:
  - "Tu día" (daily work) and "Tu negocio" (one-time setup).
  - Subtitles are link descriptions (`aria-describedby`), so link names stay
    "Agenda", "Cuotas"…
  - A red dot marks setup sections that are still pending (`lib/setup-steps.ts`).
  - Phones: four tabs plus "Más", a sheet with every section.
- **Setup guide** (`lib/setup-steps.ts` + `components/home/setup-guide.tsx`):
  - two milestones, build then use
  - the current step shows why it matters, a preview of what it produces
    (`components/illustrations/previews.tsx`) and what it unlocks
  - once everything is done, Inicio leads with "Qué hacer cada día"
- **Welcome tour** (`components/home/welcome-tour.tsx`):
  - opens on `/dashboard?bienvenida=1` (right after onboarding, or from the
    user menu "¿Qué hace Agenda?")
  - closing it removes the parameter
- **Page headers** take `help={{ section, settings, open }}`. Pass
  `open: true` while the section is empty; the viewer's choice is remembered
  in localStorage.
- **Configuración** is split into tabs (`?seccion=negocio|reservas|cuotas|recordatorios`)
  that can be deep-linked.

## Reminders

- `reminders` is an outbox: one row per (turno or cuota, kind), unique, so
  the job never plans or sends the same reminder twice.
- Kinds:
  - turnos: the day before (`appointment_24h`), and 2 h before (opt-in)
  - cuotas: N days before, on the due day at 09:00 local time, and N days
    after if still unpaid
- All timings are in Configuración → Recordatorios.
- Channel: **email** when the client has one (sent automatically by
  `/api/cron/run`, up to 3 attempts). Otherwise **WhatsApp manual**: the
  reminder waits in Recordatorios with a pre-written `wa.me` link, and tapping
  it marks it sent (with undo).
- WhatsApp Business API and SMS are placeholders behind the same
  `MessageChannel` interface (`lib/messaging/`).
- Reminders that are no longer needed (turno cancelled, cuota paid, unsent
  for 3 days) are marked "skipped".
- Members only see turno reminders of their own staff record.
- Hosting the scheduler: see [`docs/cron.md`](docs/cron.md) (Vercel Cron,
  crontab, Docker profile, `npm run cron:run`).

## Online payments

No provider is integrated yet. `lib/payments/` defines `PaymentProvider`
(`createSubscription`, `cancelSubscription`, `handleWebhook`), plus a `manual`
provider (today's behavior) and an HMAC-signed `fake` one for tests. Webhook
payments become regular `payments` rows (method `online`), applied to the
oldest unpaid cuotas; events are deduplicated in `payment_events`. How to plug
in Bancard, Pagopar and others: [`docs/payment-providers.md`](docs/payment-providers.md).

## Production

Docker on one VPS: Caddy (automatic HTTPS) → Next.js standalone image →
Postgres, plus a scheduler and nightly backups. CI tests every push and
publishes the image to GHCR from `main`.

Step by step (server, DNS, SMTP, first deploy, updates, rollback, backups):
[`docs/deploy.md`](docs/deploy.md). The production files are in [`deploy/`](deploy).

- **Emails:** `EMAIL_TRANSPORT=smtp` with any provider (`lib/email/smtp-transport.ts`).
- **Strict settings:** the image sets `DEPLOYMENT=production`, and `lib/env.ts`
  then refuses console email, `RATE_LIMITS=off`, the fake payment provider
  and non-https URLs.
- **Migrations:** `scripts/migrate.mjs` (`npm run db:migrate:prod`) runs before
  the app starts.
- **Monitoring:** `GET /api/health` checks the app and the database.

## Conventions

- Timestamps: `timestamptz`, stored in UTC. Business default timezone:
  `America/Asuncion`.
- Money: integers in the currency's minor unit, with a `currency` column.
  Default `PYG` (no decimals).
- UI copy in Spanish (es-PY); code and comments in English.
- Phones: stored in E.164 (`+595981123456`), unique per business; typed and
  shown as `0981 123 456`. C.I.: stored without dots, shown as `4.567.890`.
  Money inputs format guaraníes with dots while typing. Times are always 24 h;
  dates use a Spanish calendar (weeks start on Monday).
- Availability: weekly rules per staff member, as wall-clock times in the
  business time zone (ISO weekday 1 = Monday). Blocked slots are UTC instants;
  `staff_id = null` blocks the whole business.
- Clients, services and staff are archived, not deleted (appointments will
  reference them).
